# Модуль users

Хранит пользователей и отдаёт их профили. Здесь же лежит `passwordHash`, который читается только для проверки пароля из модуля `auth`.

## Файлы

| Файл | Роль |
| --- | --- |
| `entities/user.entity.ts` | Таблица `user` |
| `users.service.ts` | Доступ к БД, проверка прав, сборка профиля для ответа |
| `users.controller.ts` | HTTP-маршруты `/users` |
| `user.policy.ts` | Правила: кто что может делать с профилем |
| `dto/update-user.dto.ts` | Что можно менять через `PATCH` |
| `dto/create-user.dto.ts` | Внутренний тип для регистрации (не тело запроса) |
| `users.module.ts` | Подключает репозиторий, политику, экспортирует `UsersService` |

## Как это работает

### Сущность

`email` и `username` уникальны на уровне БД. `passwordHash` помечен `select: false`: обычные запросы его не возвращают. Единственное место, где он читается, — `UsersService.findCredentials`. Оттуда пользователь возвращается без хеша, а хеш отдельно.

### Два набора методов в сервисе

1. **Внутренние** (`create`, `findOne`, `findByEmail`, `findByUsername`, `findById`, `findCredentials`, `updatePasswordHash`): без проверки прав. Их вызывает модуль `auth` (регистрация, вход, поиск пользователя по сессии или токену).
2. **Для контроллера** (`listProfiles`, `getProfile`, `updateProfile`, `removeProfile`): сначала `authorizationService.authorize(UserPolicy, ...)`, потом действие. Эти методы нельзя вызывать мимо политики.

### Маршруты

| Маршрут | Доступ |
| --- | --- |
| `GET /users`, `GET /users/:id` | все, включая гостей |
| `PATCH /users/:id` | только сам пользователь |
| `DELETE /users/:id` | только сам пользователь (204) |

Глобальный гвард авторизации закрывает маршрут без объявления, поэтому у каждого метода есть `@Can.Anyone()`. Для чтения добавлен `@Authenticate({ optional: true })`: гость проходит с `user = null`, вошедший получает своего пользователя. Без этого гость получил бы 401 до проверки политики.

Права проверяет сервис, а не маршрут, потому что нужна загруженная запись: политика сравнивает `user.id` с `target.id`.

### Политика (`UserPolicy`)

- `view` — всегда `true`: профили публичные.
- `update`, `delete` — `user.id === target.id`. Параметр `user` типизирован как `User` без `null`: эти способности вызываются только для вошедших.

### Скрытие email

`toProfile()` убирает `email` из ответа, если смотрит не владелец профиля. Политика отвечает «можно ли видеть профиль», а какие поля показывать, решает сервис.

### Обновление профиля

`UpdateUserDto` содержит только `username`, `firstName`, `lastName`. Он **намеренно не наследует** `CreateUserDto`: там есть `passwordHash` и `email`, и через `PATCH` можно было бы подставить чужой хеш. Глобальный `ValidationPipe` с `whitelist: true` дополнительно отбрасывает лишние поля. Занятый username даёт 409 (ловится код PostgreSQL `23505`).

## Ограничения

- `isActive` в сущности есть, но нигде не проверяется.
- Email и пароль через `PATCH` менять нельзя: для этого нужны отдельные безопасные сценарии (подтверждение email, смена пароля).
- Роли пользователей не заведены, администратора нет.
- Проверялись только компиляция и юнит-тесты. Маршруты вручную не вызывались.
