# Что реализовано в проекте

Документ описывает аутентификацию, авторизацию, посты и пользователей. Код прокомментирован, здесь — общая картина и причины решений.

## 1. Общая схема запроса

```
запрос → AuthenticationGuard → AuthorizationGuard → ValidationPipe → контроллер → сервис → политика
         (кто ты?)             (есть ли объявление  (проверка DTO)                         (можно ли тебе
          кладёт user          на маршруте?)                                                это сделать?)
          в request.user
```

1. **Аутентификация** определяет, кто делает запрос (cookie-сессия или Bearer JWT), и кладёт пользователя в `request.user`.
2. **Авторизация** проверяет права. Глобальный гвард **закрывает по умолчанию**: маршрут без `@Can()`, `@Can.Anyone()` или `@Public()` недоступен (403 для пользователя, 401 для гостя).
3. **ValidationPipe** проверяет тело запроса по DTO.
4. Сервис загружает запись и вызывает **политику** (`authorize()`), которая решает, можно ли это делать с этой записью.

Порядок модулей в `app.module.ts` важен: `AuthenticationModule` стоит перед `AuthorizationModule`, иначе авторизация видела бы всех как гостей.

## 2. Аутентификация (`src/auth`)

Два способа входа:

| Способ | Для кого | Эндпоинты |
| --- | --- | --- |
| Cookie-сессия | Браузер | `POST /auth/sign-up`, `/auth/sign-in`, `/auth/sign-out` |
| JWT (access + refresh) | Мобильные клиенты | `POST /auth/token`, `/auth/token/refresh`, `/auth/token/revoke` |

- **Настройки** (`app.module.ts`): `AuthenticationModule.forRootAsync` берёт ключ из `JWT_SECRET` (не короче 32 байт, без него приложение не стартует). Access-токен живёт 15 минут. Сессия — не больше 14 дней и не больше 3 дней без активности. Issuer и audience настраиваются через `JWT_ISSUER`, `JWT_AUDIENCE`.
- **`CredentialsService`**:
  - Email нормализуется (`trim`, `NFC`, нижний регистр).
  - Пароль хешируется `PasswordHasher` (scrypt).
  - Для неизвестного email проверяется фиктивный хеш, поэтому по времени ответа нельзя узнать, какие email зарегистрированы.
  - Если параметры хеширования изменились, хеш обновляется после успешного входа (`needsRehash`).
  - Дубликат email или username при одновременных регистрациях даёт 409 (ловится код PostgreSQL `23505`).
- **Провайдеры**: `SessionAuth` (cookie) и `JwtAuth` (Bearer) превращают сессию или токен в пользователя.
- **Refresh-токены одноразовые**: повторное использование старого токена отзывает всю цепочку.
- **`/auth/token/revoke`** всегда отвечает 204, чтобы не раскрывать, существовал ли токен.
- **`passwordHash`** (`select: false`) читается в одном месте — `UsersService.findCredentials`, откуда пользователь возвращается без хеша.

## 3. Авторизация и политики

Политика — класс с `@Policy()`, где каждый метод отвечает «может ли пользователь сделать это». Разрешает только литеральный `true`.

Где проверять:
- **На маршруте** (`@Can(Policy, 'ability')`) — если проверка не зависит от записи (например, «может ли вошедший создавать»).
- **В сервисе** (`authorizationService.authorize(...)`) — если нужна загруженная запись. Тогда на маршруте стоит `@Can.Anyone()`, а сервис принимает решение.
- **Списки** фильтруются в запросе к БД, а не политикой по одной записи.

Коды ответов: гость, которому отказала политика, получает 401; вошедший пользователь — 403; отсутствующая запись — 404.

Тип параметра `user` в политике имеет значение: `User | null` — способность работает и для гостей; `User` — только для вошедших (компилятор не даст передать гостя).

### `PostPolicy` (`src/posts/post.policy.ts`)

| Способность | Правило |
| --- | --- |
| `view` | опубликованный пост — всем; черновик — только автору |
| `create` | любой вошедший |
| `update`, `delete` | только автор |

### `UserPolicy` (`src/users/user.policy.ts`)

| Способность | Правило |
| --- | --- |
| `view` | профили публичные, видят все |
| `update`, `delete` | только сам пользователь |

## 4. Посты (`src/posts`)

Сущность `Post`: `id`, `content`, `published` (по умолчанию `true`; `false` — черновик), `authorId`, `author`, `createdAt`. Автор берётся из токена или сессии, а не из тела запроса.

| Метод и путь | Доступ |
| --- | --- |
| `POST /posts` | вошедшие (`@Can(PostPolicy, 'create')` на маршруте) |
| `GET /posts` | все; гость видит опубликованные, вошедший — ещё и свои черновики |
| `GET /posts/:id` | все, но черновик — только автору |
| `PATCH /posts/:id` | автор |
| `DELETE /posts/:id` | автор, ответ 204 |

Чтение идёт с `@Authenticate({ optional: true })`: гость проходит с `user = null`, а вошедший получает своего пользователя.

Таблица создаётся миграцией `src/database/migrations/1793600000000-AddPost.ts` (внешний ключ на автора, каскадное удаление).

## 5. Пользователи (`src/users`)

| Метод и путь | Доступ |
| --- | --- |
| `GET /users`, `GET /users/:id` | все; **email видит только владелец профиля** |
| `PATCH /users/:id` | только сам пользователь |
| `DELETE /users/:id` | только сам пользователь, ответ 204 |

`UpdateUserDto` содержит только `username`, `firstName`, `lastName`. Он **не наследует** `CreateUserDto`: иначе через `PATCH` можно было бы подставить чужой `passwordHash` или `email`. Занятый username даёт 409.

## 6. Валидация

В `main.ts` включён глобальный `ValidationPipe({ whitelist: true, transform: true })`:
- проверяет тела запросов по декораторам `class-validator`;
- `whitelist` отбрасывает поля, которых нет в DTO;
- `transform` превращает JSON в экземпляры DTO.

Для работы нужен пакет `class-transformer`, он добавлен в зависимости.

## 8. Запуск и настройка

Переменные в `.env`: настройки PostgreSQL (`HOST`, `DB_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`), `JWT_SECRET`, при необходимости `PORT`, `JWT_ISSUER`, `JWT_AUDIENCE`.

```bash
npm run migration:run   # применить миграции, в том числе таблицу post
npm run start:dev
npm test
```

## 9. Что осталось сделать

- **Проверить вручную** в работающем приложении: регистрацию и вход, права на посты и профили, что `passwordHash` не попадает в ответы.
- **Хранилище сессий для продакшена.** При `NODE_ENV=production` сессии в памяти не допускаются, нужно подключить хранилище (БД, Redis). Эту часть документации по аутентификации я прочитал не полностью.
- **Роли** (staff, admin) в `User` не заведены: модерации чужих постов нет. Её можно добавить через роли и хук `before()` в политике.
- **E2E-тесты** и юнит-тесты для сервисов: пока есть только тесты политики постов и контроллера.
- **Email не подтверждается**, сброса пароля нет.
